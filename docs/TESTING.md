# Oxicale Testing Strategy

Status: Draft 1

Testing must cover protocol correctness, data safety, security boundaries and
the two product-defining features: zero-choice onboarding with mixed calendars,
and server-side subscriptions with filtered feeds.

## 1. Test pyramid

### 1.1 Unit tests

- Path parsing, percent-decoding and traversal rejection.
- Username and slug validation.
- iCalendar parsing, validation and canonicalisation.
- vCard parsing and validation.
- Recurrence expansion and time-range matching.
- Feed filtering, timezone merging and deterministic output.
- Sync token encoding, expiry and invalidation.
- Subscription URL policy and SSRF decisions.
- Backoff and scheduling calculations.
- Token generation, hashing, redaction and expiry.
- Encryption and decryption of remote credentials.
- Configuration parsing, defaults and precedence.

### 1.2 Component tests

- Storage transactions, atomic writes and crash recovery.
- Index rebuild and repair.
- Collection metadata round-trips.
- Authentication backends.
- Rights decisions.
- XML serialisation and error preconditions.

### 1.3 Integration tests

- Full HTTP request/response through the server router.
- DAV discovery and CRUD.
- Report filtering and sync.
- Subscription fetch with a mock HTTP server.
- Feed endpoint with conditional requests.
- Web UI flows with a headless browser.
- Import from a fixture Radicale data directory.
- Restart and recovery scenarios.

### 1.4 Conformance and compatibility tests

- CalDAV/CardDAV protocol conformance.
- Real client smoke tests where automation is possible.
- Interoperability fixtures generated by common clients.
- Regression tests for each fixed compatibility bug.

### 1.5 Security tests

- SSRF: loopback, private, link-local, metadata, DNS rebinding, redirect to
  private, IPv6-mapped IPv4.
- XML: DTD, external entity, oversized depth, billion laughs.
- Auth: brute force rate limit, username enumeration, session fixation, CSRF.
- Tokens: unknown, revoked, expired, timing, log redaction.
- Path traversal and symlink attacks.
- Resource exhaustion: oversized bodies, many components, expensive recurrence.
- Fuzzing for parsers and URL handling.

## 2. Tooling

Proposed:

- `cargo test` for unit and integration tests.
- `cargo nextest` for faster CI runs.
- `proptest` for property-based tests of parsers and path handling.
- `cargo-fuzz` targets for iCalendar, vCard, XML and URL parsing.
- `wiremock` or a local Axum test server for subscription HTTP fixtures.
- `tempfile` and a temporary SQLite database for storage tests.
- `insta` or explicit fixtures for XML responses and feed output.
- `playwright` or `chromium` headless for web UI tests (optional in CI).
- `cargo audit` and `cargo deny` for dependency and license checks.
- `criterion` for query and feed generation benchmarks.

## 4. Required test scenarios

### 4.1 Onboarding and mixed calendars

- First login creates exactly one default calendar and, when enabled, one
  default address book.
- Repeated login does not duplicate collections.
- The default calendar accepts `VEVENT`, `VTODO` and `VJOURNAL`.
- `MKCALENDAR` with `VTODO` only results in a mixed calendar.
- The web UI has no type selector in the first-run flow.
- Deleting the default calendar and logging in again recreates it.
- Importing a typed Radicale calendar yields a mixed calendar with all items.

### 4.2 CalDAV/CardDAV

- Discovery from root to collections.
- `PROPFIND` depth 0 and 1.
- `GET`/`HEAD` on collection and item.
- `PUT` create, update and replace with preconditions.
- `DELETE` item and collection.
- `MOVE` item within a collection.
- `calendar-query` with time range, component filter, text match and property
  filter.
- `calendar-multiget` with missing and duplicate hrefs.
- `free-busy-query` with recurrence and limits.
- `sync-collection` full and incremental.
- Invalid sync token triggers full resync.
- CardDAV query and multiget.
- UID conflicts return the correct precondition.
- Read-only subscriptions reject writes with `403`.
- Unsupported components return `415`.

### 4.3 Subscription fetching

Use a controllable mock server to test:

- Initial fetch success stores items.
- Initial fetch failure does not create a collection.
- `200` with new content updates items atomically.
- `304` does not change ETags or sync tokens.
- Remote deletion removes the local item.
- Remote UID change is delete plus create.
- Invalid ICS on refresh preserves the last good content.
- HTTP 500 on refresh preserves content and marks degraded.
- 404/410 on refresh preserves content and marks degraded.
- Redirect chains up to the limit succeed; beyond the limit fail.
- Redirect to a private address fails.
- Credentials are sent only to the intended origin.
- Conditional headers are sent when validators exist.
- Response size and component limits are enforced.
- Refresh is jittered and respects the minimum interval.
- Concurrent refreshes of the same subscription do not duplicate work.
- Restart recalculates due subscriptions from metadata.

### 4.4 Feeds

- Create a `VTODO` feed; output contains only tasks.
- Create an `VEVENT` feed; output contains only events.
- Create a mixed filter; output contains selected types.
- Feed output contains required timezones.
- Feed output is deterministic and ETag-stable for unchanged data.
- Adding an excluded component does not necessarily change the feed ETag.
- Adding an included component changes the ETag.
- Conditional GET returns `304`.
- Revoked token returns `404`.
- Expired token returns `404`.
- Rotated token invalidates the old URL.
- Unknown token and revoked token have identical responses.
- Feed URL is not present in logs.
- Feed works from a subscription collection.
- Feed is limited by rate limit.

### 4.5 Security

- Subscription to `http://127.0.0.1`, `http://[::1]`, `http://169.254.169.254`,
  `http://10.0.0.1` and IPv4-mapped IPv6 equivalents is rejected.
- DNS rebinding is prevented by connecting to the validated address.
- XML with `<!DOCTYPE` is rejected.
- External entities are not resolved.
- Oversized bodies return `413`.
- Path traversal through encoded `..` and `%2f` is rejected.
- Symlinks in the data directory are not followed.
- Login rate limiting works.
- CSRF protection rejects missing/invalid tokens.
- Secrets are absent from logs in all failure paths.
- Feed token comparison is constant time (code review plus targeted test).
- TLS configuration rejects invalid certificates or keys.

### 4.6 Storage and recovery

- Kill the process during a write; restart; no partial item is visible.
- Remove the index; rebuild; all items and metadata survive.
- Corrupt an item; verification reports it.
- Restore from backup; verification passes.
- Sync tokens become invalid after index rebuild and clients resync.
- Metadata writes are atomic.
- Feed token hashes survive restart.
- Encrypted subscription credentials survive restart with the key.

### 4.7 Core client contract suite

`crates/oxicale/tests/compat.rs` is the automated gate for the core-client
compatibility contract. It uses only the public HTTP surface and must not call
storage internals.

Required scenarios:

- Root discovery and direct principal discovery return the same homes.
- Default mixed calendar and address book are discoverable.
- `MKCALENDAR` with a narrowed component set still yields a mixed calendar.
- Calendar item create, conditional update, delete and move.
- `calendar-query` with a time range and component filter.
- Recurring event expansion returns all matching occurrences.
- Full and incremental `sync-collection`, including delete tombstones.
- Address book create, item write and `addressbook-query`.
- Read-only subscription discovery and write rejection.
- Feed conditional `GET` and change tracking.
- Unsupported components return `415` with a DAV error body.
- Unsupported `calendar-data` `expand` returns an explicit error rather than
  incorrect data.

The suite is intentionally protocol-level. Real-client smoke tests remain a
manual release gate; use [CLIENT-CHECKLIST.md](CLIENT-CHECKLIST.md).

## 5. Acceptance test harness

A multi-client compatibility harness should:

1. Start an isolated Oxicale instance with a temporary data directory.
2. Provision a user and default calendar.
3. Run discovery with each client or a protocol script.
4. Create, update and delete all component types.
5. Create a subscription against a mock ICS server.
6. Wait for refresh.
7. Verify subscription content and read-only behaviour.
8. Create a `VTODO` feed and verify its content.
9. Restart the server and continue incremental sync.
10. Rebuild the index and verify full resync.

Where a real client cannot be automated, record a manual test script with
screenshots and observed requests.

## 6. CI plan

On every pull request:

- `cargo fmt --check`
- `cargo clippy --all-targets --all-features -- -D warnings`
- `cargo test --all`
- The core client contract suite (`cargo test -p oxicale --test compat`)
- `cargo deny check`
- `cargo audit`
- Documentation link check
- Unit and integration tests for the affected crates

Nightly:

- Fuzz targets for at least 10 minutes.
- Full compatibility harness.
- Dependency update check.
- Storage crash-injection tests.

Before release:

- Full manual client matrix.
- Radicale import of a realistic data set.
- Restore-from-backup drill.
- Security review of subscription fetching and feed tokens.

## 7. Coverage targets

- Core domain and protocol code: at least 85% line coverage.
- Security-critical code (SSRF policy, tokens, auth, path parsing): 100%
  branch coverage for decision points.
- Storage and sync: targeted tests for every documented invariant.
- Web UI: smoke tests for each primary flow; visual regression optional.

Coverage is a guide, not a substitute for scenario tests.

## 8. Release gates for the new features

The release is blocked if any of the following fails:

- A new user reaches a usable mixed calendar without seeing a type selector.
- A task-only calendar request results in a mixed calendar.
- A subscription is visible to two clients and read-only in both.
- A remote update reaches both clients via sync.
- A failed refresh preserves last-good data.
- A `VTODO` feed contains no events or journals.
- A revoked feed URL stops working immediately.
- SSRF tests pass with default configuration.
- Radicale import preserves collection paths and item hrefs.
